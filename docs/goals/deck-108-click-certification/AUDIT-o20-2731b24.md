## Trust anchors — operator decision (joins F6 + root-owned install; not this lane)

- **A1 (was H1) — the deck port is the seat's anchor.** `bin/fleetdeck-verify-answer.js:86,107-112,153`: `configured`/`sigValid` come from whatever answers on 127.0.0.1:3131. Reproduced: a fake deck + one genuine signature over attacker bytes → exit 0. A same-user process can kill the deck, bind :3131 as a proxy, and read the operator's password from the next sign-in POST (plaintext JSON). Real fix: root-owned deck service; DECK-109: PAKE (SRP-6a) or passkey instead of a password POST.
- **A2 (was H2) — 1Password approval is content-blind.** The prompt names app + key, never the bytes; `GET /api/unblock/:id` (unauthenticated) shows `clickSeen:true, sigState:null` at the moment the operator is about to approve, so a racing `ssh-keygen -Y sign` over attacker bytes can ride the same Touch ID. P6 narrows it; the real fix is a signer that shows the bytes (hardware key with display) or a per-deck key.
- **A3 (was H3 real) — `~/.fleetdeck/operator.json` is same-user-writable.** P2 makes an overwrite visible; the real fix is the same root-owned anchor.
- **A4 (was M1) — global sign-in rate limit is an operator DoS.** Five bad POSTs a minute from any same-user loop keeps the operator locked out; P4 makes it visible; no cheap fix that keeps the guard.

## What this means for promoting clicks to prod triggers (lowcap's typed-word rule)

Until A1–A3 are fixed by a root-owned deck, a verified click proves "a genuine Touch ID approval happened", not "the operator saw and chose these bytes". Keep typed word = prod trigger for prod-class actions; treat a verified click as strong evidence, not authority.
