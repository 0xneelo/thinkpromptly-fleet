## A — hunter findings (severity-ranked)

1. **High — `deploy-keys/lib/host_apply.py:154`, `deploy-keys/apply-principals-windows.ps1:21`.** An earlier `Match` block (e.g. `Match Address 10.0.0.0/8` + `PasswordAuthentication yes`) beats the appended global `PasswordAuthentication no` (first matching declaration wins). Linux validates only against `127.0.0.1`; Windows has no effective-policy check. Fix: validate with `sshd -T -C user=deploy,addr=<each non-loopback source>` (or insert the prohibition inside a `Match User deploy` block placed BEFORE any existing Match), and on Windows evaluate the effective config the same way.
2. **High — `host_apply.py:238`, `deploy-keys/lib/windows-apply.ps1:139`.** Trust and principals applies read `sshd_config` without a lock; a principals run can install a snapshot that lacks the `TrustedUserCAKeys` the trust run just wrote, and its validation still passes. Fix: one lock file per host apply (`flock` on Linux, a mutex on Windows), re-read the config after acquiring it, and assert the other run's directive is present before writing.
3. **High — `deploy-keys/verify-cert.sh:46`.** `IdentityFile`/`CertificateFile` accumulate with the alias's configured ones; `IdentitiesOnly=yes` does not exclude configured identities, so a v1 cert already on the alias can authenticate and the script prints PASS for a v2 cert that is untrusted. Fix: run with `-F /dev/null` plus explicit `-o HostName/User/Port` from `ssh -G <alias>`, or `-o IdentityFile=none -o CertificateFile=none` before the explicit pair.
4. **High — `verify-cert.sh:58`.** `--expect refused` passes on any `Permission denied` — a `ProxyJump` rejecting its credentials, or an empty credential file. Fix: require the target host key exchange to complete (`-v` marker `Authenticating to <host>:<port>`) and distinguish the refusal of the presented cert (`Server refused certificate` / `no mutual signature`) from other failures; preflight that the cert file parses with `ssh-keygen -L`.
5. **Medium — `windows-apply.ps1:143`.** Policy files are truncated and rewritten in place while sshd is live. Fix: write to a temp file in the same directory, then `Move-Item -Force` (atomic on NTFS).
6. **Medium — `host_apply.py:77`.** Under `umask 077`, `mkdir(mode=0755)` yields `0700` for `/etc/ssh/principals`; sshd reads principals files as the authenticating user and cannot traverse. Fix: `os.chmod` after mkdir (and on the files), assert the final modes.
7. **Medium — `host_apply.py:216`, `windows-apply.ps1:113`.** `--rollback` validates the CURRENT (possibly malformed) config before restoring the backup, so a broken config can never be rolled back. Fix: validate the backup, restore it, then validate.
8. **Medium — `host_apply.py:248`.** In the failure handler, a failing `usermod` (account DB locked) raises inside the handler and skips every restore below it. Fix: wrap each rollback step, collect errors, restore files first, disable the account last.
9. **Medium — `deploy-keys/mint-deploy-cert.sh:40` vs `:71`.** The CA fingerprint is classified from the pub file, then the file is re-read at signing time; a change in between yields a v1-signed cert tagged `-ca2` (or the reverse). Fix: read the pub once into a variable and sign from that exact content (temp file with `umask 077`).
10. **Medium — `verify-cert.sh:64`.** Windows output is `IVO_CERT_OK deploy\r\n`; `grep -qx` rejects the marker because CR survives. Fix: `tr -d '\r'` before comparison.
11. **Medium — `verify-cert.sh:50`.** A certificate path with spaces is reparsed by ssh's config parser (`CertificateFile=/tmp/cert set/...`). Fix: pass `-o 'CertificateFile="<path>"'` with quotes ssh understands, or refuse paths with whitespace.
12. **Low — `deploy-keys/bootstrap-rog-strix.sh:15`.** The newline guard `*'\n'*` matches a literal backslash-n (`C:\new-ca.pub`). Fix: test with `case "$p" in *"$(printf '\n')"*)`.

Not flagged by the hunter (treat as not-yet-confirmed clean, not proven): `render-sudoers.sh`, `setup-german-box-ca.ps1`, `setup-rog-strix-ca.ps1`, the `server.js` mint-route hunk.
